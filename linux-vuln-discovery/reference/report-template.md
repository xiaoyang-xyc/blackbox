# 安全测试报告模板

> 此文件为报告生成阶段按需加载。SKILL.md §5.1 定义了实时打印要求，以下定义报告结构、格式、质量规则和对账流程。

## 1. 报告结构

| 章节 | 内容 |
|------|------|
| 一、执行摘要 | 测试时间、目标、范围、总体结论、关键发现摘要 |
| 二、目标环境信息 | OS、内核、架构、运行服务、已安装软件、关键补丁级别 |
| 三、漏洞详情 | 每个漏洞的完整信息（见下方格式） |
| 四、配置基线核查 | 参照 10 号文档逐项列出达标/未达标 |
| 五、权限提升路径 | 可组合漏洞的完整攻击链 |
| 六、AI 自主延伸测试项 | 发散过程中发现的额外测试点及结果 |
| 七、风险等级汇总 | 高/中/低危分类统计 |
| 八、修复建议优先级 | 紧急/重要/建议三级排列 |
| 九、覆盖矩阵 | reference 每个文件的覆盖状态（已覆盖/未覆盖/部分覆盖） |

## 2. 漏洞详情格式

每个漏洞必须包含以下**全部字段**（缺一不可）：

```
漏洞编号: VULN-XXX
关联测试点: T-XXX-XXX（主测试全量表中的唯一 ID）
漏洞类型: [提权/认证绕过/信息泄露/...]
风险等级: [高危/中危/低危]
漏洞点: [具体文件/服务/配置，精确到路径和行号]
触发条件: [触发此漏洞需要的前置条件：权限、访问方式、特定配置状态等]
漏洞原因: [技术原理说明，为什么存在此漏洞——必须写到根因层面]
发现过程: [推理链：为什么检查此项 → 发现了什么 → 如何判断存在漏洞]
关键证据:
  命令: [实际执行的命令]
  输出: [返回的完整输出，摘录关键部分]
  分析: [从输出中得出漏洞结论的推理过程]
利用尝试记录:
  路径1: [方法描述] → 结果: 成功/失败 → 原因: [为什么成功/失败]
  路径2: [方法描述] → 结果: 成功/失败 → 原因: [为什么成功/失败]
  （至少记录 1 条利用路径，成功和失败的都要记录）
漏洞复现:
  1. 前置条件（所需权限/访问）
  2. 完整步骤（每步命令 + 预期输出）
  3. 实际输出截图/记录
影响范围: [能获取什么权限/访问什么数据/影响哪些服务]
修复建议: [具体可操作的修复方案，包含修复命令或配置变更]
```

## 3. 测试覆盖清单

报告必须包含完整的**测试覆盖清单**，每个测试点使用唯一 ID 追踪状态：

| 测试点ID | 测试项 | 来源参考文档 | 状态 | 结果 |
|----------|--------|-------------|------|------|
| T-01-001 | [测试项名称] | 01 | verified | 通过 |
| T-01-002 | [测试项名称] | 01 | risk-only | 风险项 RISK-XXX |
| T-05-015 | [测试项名称] | 05 | excluded | 目标环境不适用（无容器） |

**测试点ID格式**：`T-{文件序号}-{序号}`（如 `T-01-001`、`T-05-015`）

**状态流转（5种终态）：**

| 状态 | 含义 | 说明 |
|------|------|------|
| `pending` | 待执行 | 初始状态 |
| `testing` | 执行中 | 单点循环开始时标记 |
| `verified` | 已验证 | 已完成完整验证（通过或发现漏洞 VULN-XXX） |
| `risk-only` | 仅风险 | 已分析但无法验证利用，标记为风险项 RISK-XXX |
| `excluded` | 排除 | 目标环境不适用，必须注明排除原因 |

- 覆盖清单必须涵盖全部 337 项测试点（SKILL.md v3.0 阶段二内嵌）
- 每个测试点从 `pending` 开始，必须流转到终态（`verified` / `risk-only` / `excluded`）
- `excluded` 状态必须注明具体原因（如"目标环境不适用：无容器运行时"）
- 覆盖率必须在报告摘要中明确标注（如"覆盖率: 100%（N verified / M risk-only / K excluded）"）

## 4. 报告质量硬性规则

> §2 字段模板 + 以下规则 = 完整报告质量标准。违反即报告无效。

| 规则 | 要求 | 违反示例 | 正确示例 |
|------|------|---------|---------|
| 禁止模糊描述 | 不得出现"可能/疑似/潜在"，§2.3 已定义三态标准 | "可能存在提权漏洞" | "已确认提权，`xxx` 输出 `uid=0(root)`" |
| 利用尝试必填 | §2 利用尝试记录字段必填 | 空白 | 命令+输出+分析完整记录 |
| 验证必须实际执行 | 命令→输出→分析三段缺一不可，第三方可复现 | 仅给结论 | 完整命令+输出+推理 |
| 风险项必须有失败原因 | ❌"利用条件复杂" ✅"3种方法均失败：原因1/2/3" | 模糊原因 | 逐条失败原因 |
| 覆盖矩阵必含 | 报告第九章列出全部 337 项测试点覆盖状态 | 缺失 | 已覆盖/未覆盖/部分覆盖 |

## 5. 测试点对账

> 确保每个测试点有确定状态，消除"静默遗漏"。对账输出附在报告末尾。

**对账流程：** 从主测试全量表提取所有 ID → 检查终态（verified/risk-only/excluded）→ 统计 → 检查 excluded 原因合理性

**硬性要求：** `pending` 必须为零 | excluded 必须有环境证据 | 覆盖率数字与对账一致

**对账输出格式：**
```
=== 测试点对账报告 ===
总测试点数: N
verified: X 项（含 VULN-xxx Y 个）| risk-only: M 项（含 RISK-xxx K 个）
excluded: Z 项（附排除原因明细）| pending: 0 项（必须为零）
覆盖率: 100%
排除原因明细: T-08-001: 无容器运行时 / T-08-002: 无K8s / ...
